## 1. Итог в пяти пунктах

1. **Память.** 12 МП → ×4 (16000×12000) проходит с пиковым RSS **212 МБ** на CPU с T=128 (аналог T0) и **354 МБ RSS / ≤ 504 МБ RSS+память iGPU** на Intel UHD 730 с T=256 (аналог T1). Выход целиком в памяти не собирается: одновременно живут не больше двух полос. Экспорт JPEG/PNG из BandStore занимает ~1 полосу + 10 МБ.
2. **I/O не узкое место.** Запись 576 МБ полос с fsync занимает 0.5–1.1 с: это 0.4–0.8% времени SR на CPU/iGPU и ~8% на RTX 3060. Запись идёт в фоновом потоке, и видимое ожидание ≤ 1%. **LZ4 бесполезен:** выход SR сжимается всего на 3.6% (576 → 555 МБ).
3. **Время упирается в инференс.** Для compact SR это ~10–12.6 с на МП входа на десктопном CPU (8 потоков) и на UHD 730; ×2 стоит столько же, сколько ×4, а «быстрый 2×» в 4 раза дешевле. Из экспорта дорог только PNG: 63 с при zlib level 6 и 10 с при level 1 на 192 МП.
4. **Швы.** Pad 16 достаточно: внутри изображения PSNR тайлового выхода против прохода целиком 66–75 дБ, максимальная ошибка на шве ≤ 9/255. Метрика градиента на шве совпадает с эталоном с точностью ±0.01. **Feather не даёт измеримого выигрыша.** Pad 32 (≈ рецептивное поле 34 px) даёт почти точное совпадение (≤ 1/255). Формулировка NFR-QLT-003 в нынешнем виде **не выполняется даже на изображении без тайлов** (1.67–1.85 > 1.5), её нужно переписать.
5. **Resume:** 7 прогонов с `kill -9` (CPU/iGPU/RTX, raw/LZ4, feather, sync/async) дают **побайтно идентичные JPEG и PNG**. Терялась только недоделанная полоса: ≤ 6 с работы на CPU и ≤ 10 с на iGPU.

Два побочных, но важных наблюдения о ncnn Vulkan (§6.4): **проход 1.2 МП целиком на UHD 730 молча даёт мусор**, а **тайл 512 на обоих GPU даёт локальные ошибки до 164/255**. На CPU обоих эффектов нет. Тайл на Vulkan пока ограничиваем 256.

## 2. Условия GO

1. Тайл по умолчанию: T0 = 128 (CPU), T1 = 256, T2 = 256. **512 не использовать**: на CPU пик 1.08 ГБ, на Vulkan ошибки (§6.4), а выигрыш в скорости 256 → 512 всего 5–9%.
2. Pad 16 для compact, feather выключен по умолчанию (код оставить под флагом для x4plus/новых моделей, у которых pad меньше рецептивного поля).
3. Полосы хранятся несжатыми (raw RGB8). LZ4 не включать.
4. Проверка корректности GPU-бэкенда (микробенчмарк 05 §6.2) должна идти **на рабочем размере тайла**, а не только на 128: ошибки §6.4 проявляются только на больших формах.
5. Экспорт PNG — zlib level 1–3, а не 6 (по умолчанию в libpng).
6. Мобильные замеры (S2b): время на T0/T1/T2, троттлинг, батарея, HeifWriter / CGImageDestination, скорость UFS/eMMC.

## 3. Условия эксперимента

- **Машина:** Intel Core i5-12400 (6P/12T), 30 ГБ RAM, NVMe (ext4). Vulkan: 0 = NVIDIA RTX 3060 (дискретная, VRAM не входит в RSS), 1 = **Intel UHD 730** (встроенная, ближайший прокси мобильного GPU), 2 = llvmpipe (не использовалась).
- **Сборка:** C++20, g++ 15, ncnn 20261009 (static, Vulkan), libjpeg-turbo static **без SIMD** (JPEG медленнее продакшена, см. §5.4), lz4 1.10 static, системный libpng 1.6.
- **Модель:** Real-ESRGAN realesr-general-x4v3 (SRVGGNetCompact, 1.2M параметров, 34 свёртки 3×3, то есть рецептивное поле ±34 px входа), уровень денойза 0.5, `sr_compact_dn050`. CPU: fp16 storage (на x86 арифметика фактически fp32); Vulkan: fp16 storage + arithmetic.
- **Данные** (CC0, Wikimedia Commons):
  - 12 МП: [Avignon — Rue de la Carreterie — Baladine.jpg](https://commons.wikimedia.org/wiki/File:Avignon_-_Rue_de_la_Carreterie_-_Baladine.jpg), 4000×3000, Pixel 9a, автор Romainbehar, CC0.
  - 1.2 МП: [Stockholm (19097231126).jpg](https://commons.wikimedia.org/wiki/File:Stockholm_(19097231126).jpg), 1280×960, LG-E440, автор fotokoci (Flickr), CC0.
- **Тайлинг:** T — ядро тайла во входных px, вход сети (T+2P)²; reflect-паддинг на краях изображения; последний ряд и столбец сдвигаются внутрь (форма фиксирована); полоса = ряд тайлов. Feather (опция) — линейный, F px выхода сразу за линией владения, данные соседнего тайла берутся из его паддинга. Для вертикальных швов «хвост» полосы сохраняется в `NNNN.tail`, чтобы resume работал.
- **BandStore:** `job/bands/NNNN.raw|.lz4`. Каждый файл пишется во временный → fsync → rename → fsync каталога, затем так же атомарно обновляется `checkpoint.json {band_idx, recipe_hash, model_sha256, input_sha256, backend, tile, pad, feather, scale, format}`. Запись идёт в отдельном потоке с глубиной очереди 1, так что в RAM не больше двух полос. Перед стартом проверяется свободное место: raw-оценка + 20% (NFR-SIZE-004).
- **Превью:** ≤ 2048 px, накапливается area-суммами по мере выхода полос (uint32, 37 МБ). При resume восстанавливается чтением готовых полос.
- **Замер:** время по стадиям через `steady_clock`. Пиковый RSS — `VmHWM`, сбрасывается (`/proc/self/clear_refs` = 5) на границе каждой стадии, поэтому есть и пики по стадиям. Для iGPU дополнительно считывается `drm-resident` из `/proc/self/fdinfo` (память GPU в системной RAM, которую VmRSS не видит). Каждый замер — один прогон под общей блокировкой стенда (параллельно шёл S3): все таймированные прогоны сериализованы, но фоновая нагрузка на машину не исключена. Повторы ключевых конфигураций расходились на ≤ 3.5%.

## 5. Швы (1.2 МП, тайловый выход против прохода целиком)

Эталон — проход целиком на CPU fp32. Метрики сравнения (`seam_metrics.py`):

- PSNR — по всему изображению и «внутри» (без 128 px у края);
- max|Δ| на швах (±2 px);
- rG — литеральная NFR-QLT-003: максимум среднего градиента поперёк линии шва к среднему градиенту остальных позиций. Считается для тайлового выхода (O) и для эталона на тех же позициях (R).

### 5.3 Выводы

- **Pad 16 достаточно** для compact: ошибка на шве ≤ 9/255 при PSNR внутри 66–75 дБ. Градиентная метрика отличается от эталона на ≤ 0.01, что на порядок ниже fp16-шума GPU (55 дБ). Визуально не различимо.
- **Pad 8 — граница:** до 24/255 и заметный рост rG (+0.04–0.06). **Pad 0 — видимые швы:** до 177/255, rG ×2.
- **Feather 8 не нужен:** выигрыш в пределах шума, иногда хуже.
- **Pad 32 ≈ рецептивное поле:** совпадение до 1/255, но стоит +44% вычислений при T=128 (192² против 160²) и +23% при T=256. Не нужен.
- **NFR-QLT-003 в нынешней формулировке некорректна:** на эталоне без единого шва отношение «градиент на линии / средний внутри» уже 1.67–1.85 (> 1.5), потому что градиент сильно зависит от содержимого. Нужно сравнивать с эталоном (§8).

## 6. Прочие находки

### 6.1 Resume

| Тест | Бэкенд | Kill | Checkpoint при kill | Продолжение с | JPEG / PNG |
|---|---|---|---|---|---|
| cpu_t128_raw (×2: сразу после commit и внутри полосы) | CPU, T=128, async | полоса 13 из 24 | 12 | 13 | ✅ идентичны / ✅ |
| cpu_t128_syncio (×2) | CPU, T=128, sync | полоса 13 из 24 | 12 | 13 | ✅ / ✅ |
| vk1_t256_lz4 (×2) | UHD 730, T=256, LZ4 | полоса 7 из 12 | 6 | 7 | ✅ / ✅ |
| vk0_t256_feather8 | RTX 3060, T=256, feather 8 (с `.tail`) | полоса 7 из 12 | 6 | 7 | ✅ / ✅ |

- Во всех 7 прогонах JPEG и PNG побайтно совпадают с непрерывным прогоном (SHA-256 в `out/resume*/…/kill.txt`). Хэши CPU-прогонов с sync и async I/O тоже совпадают между собой: ncnn детерминирован при одинаковом бэкенде.
- Потеря работы — только полоса, которая считалась в момент kill: ≤ 6.4 с на CPU (T=128) и ≤ 10.4 с на UHD 730 (T=256).
- При асинхронной записи теоретический худший случай — «полоса в писателе + полоса в расчёте», то есть < 2 полос. Окно уязвимости равно времени записи полосы (40–100 мс на NVMe, ~0.3 с на eMMC `[оценка]`) против 5–10 с расчёта. Чтобы гарантировать ≤ 1 полосы, допустимо писать синхронно: на T0/T1 это стоит < 1% времени, а память даже меньше на одну полосу.
- На resume превью пересобирается чтением готовых полос (0.15–0.35 с на 288–312 МБ из кэша), хвост feather берётся из `.tail`. Несовпадение recipe_hash, model_sha256 или backend даёт отказ, а не смешивание.

### 6.2 Доля I/O и CPU-накладных

- На CPU и iGPU (аналоги T0/T1) инференс занимает **99%** времени SR, запись полос — ≤ 1%, prep/post — ~0.5%.
- На быстром GPU (RTX, по скорости ближе к T2/NPU) prep+post (вырезка, нормализация, квантование) занимают 0.65 с из 5.9 (**11%**, последовательно в том же потоке), запись полос — 8% (в фоне). На мобильном T2 с относительно слабым CPU доля prep/post будет выше. Конвейер `prep → infer → post` с очередями (05 §3) в спайке не реализован, но для T2 он нужен.

### 6.3 Диск

BandStore = ровно `out_w × out_h × 3`: 576 МБ для ×4, 144 МБ для ×2. Это совпадает с ADR-0004 («до ~600 МБ»). С проверкой NFR-SIZE-004 (+20%) нужно ≥ 691 МБ свободного места.

### 6.4 ncnn Vulkan: ошибки на больших формах (не найдена причина)

- **Проход целиком 1280×960 на Intel UHD 730 (fp16)** даёт испорченную нижнюю часть выхода: строки 1652–3827, 96 тыс. px с ошибкой > 20/255, PSNR 37 дБ против CPU. Ошибок драйвер не выдаёт. Гипотеза (не проверена — `vulkaninfo` недоступен): промежуточный тензор 1280×960×64×fp16 = 157 МБ превышает `maxStorageBufferRange` устройства.
- **Тайл 512 (вход 544²) на RTX 3060 и на UHD 730** даёт локальные ошибки до 164/255 (0.4% px > 4/255), сосредоточенные у горизонтального шва полос. PSNR 46 дБ против 54–57 дБ при T=256. На CPU с T=512 ошибок нет (74.8 дБ внутри). Причина не найдена: ncnn Vulkan, оба вендора, значит, скорее ncnn, чем драйвер.
- Следствия:
  1. Вход сети на Vulkan пока ≤ 288² (T=256 + 2·16).
  2. Проверка корректности бэкенда (05 §6.2) — на рабочем размере тайла.
  3. В S3 добавить проверку больших форм и лимитов буферов.

### 6.5 HEIC (не тестировалось — Linux)

Схема подключения платформенных кодеров к BandStore:

- **Android `HeifWriter`** (androidx.heifwriter) в режиме `INPUT_MODE_BITMAP`. Кодирует сеткой тайлов 512×512 (HEVC tile grid) и принимает `addBitmap` целого изображения. Потоковая подача — через `INPUT_MODE_BUFFER` (YUV-кадры). Ридер BandStore читает полосу за полосой и конвертирует RGB → YUV420, но кодер ждёт кадр целиком. Значит, нужен либо промежуточный YUV в памяти (192 МП × 1.5 = 288 МБ — **превышает T0**), либо ограничение HEIC выходом ≤ ~48 МП и/или ≤ 8192 по стороне (лимит HEVC-кодера на многих SoC — 4096 или 8192 на кадр; grid обходит это ценой собственной реализации). Что нужно проверить в S2b: максимальный размер, поддерживаемый `HeifWriter` на T0/T1, пиковую память и возможность собственного grid-кодирования через `MediaCodec` (HEVC тайлами 512 + сборка HEIF-контейнера).
- **iOS `CGImageDestination`** с `CGImage`, созданным через `CGDataProvider(sequentialCallbacks:)` или `directCallbacks`. Провайдер отдаёт байты по запросу из полос BandStore (ридер — тот же `read_band`). ImageIO может всё равно материализовать изображение целиком (поведение не документировано) — это главный вопрос к S2b: замер `phys_footprint` при HEIC 192 МП и 48 МП. Запасной путь — HEIC только до T-зависимого предела, выше — JPEG.
- Что осталось проверить: лимиты размера, пиковую память, время кодирования, корректность EXIF/ICC (ADR-0013/0018).

## 7. Оценка для мобильных (→ S2b)

Замеров на телефонах нет. Оценка исходит из измеренной эффективности на десктопе: 12 МП ×4 при T=128 ≈ 2.4 ТФЛОП/МП × 1.56 (паддинг) → CPU i5-12400 ~0.32 ТФЛОПС эффективно, UHD 730 ~0.30 ТФЛОПС (S1 для GFPGAN: 0.37). Соотношения устройств взяты те же, что в S1 §5: T2 ≈ 3–4× UHD 730, T1 ≈ 1× UHD 730, T0 CPU (4×A55) ≈ 10× медленнее десктопного CPU. Тепловое замедление на длительной нагрузке не учтено; по оценке 05 §8 оно даёт +30–50%.

| Сценарий | T0 (CPU A55) | T1 (≈ UHD 730) | T2 (Adreno 740 / A17) | Текущая норма T0 / T1 / T2 |
|---|---|---|---|---|
| NFR-PERF-001: 1 МП → 4× | ~120–140 с ❌ | ~10–13 с ⚠️ | ~3–4 с ⚠️ | 40 / 12 / 4 с |
| То же для 0.5 МП (предел T0 по 05 §4) | ~60–70 с ❌ | — | — | |
| NFR-PERF-002: 12 МП → 2× (T0 — быстрый 2×) | ~6 мин ❌ | ~2.1 мин (+троттлинг → 2.7–3.1) ⚠️ | ~35–45 с ✅ | 4 / 3 мин / 60 с |
| Экспорт 16 МП JPEG (NFR-PERF-012) | ≤ 4 с ✅ | ≤ 1 с ✅ | ✅ | 20 / 10 / 5 с |

Память не зависит от скорости устройства, поэтому измеренные цифры переносятся напрямую (при fp16 на ARM CPU активации примерно в 2 раза меньше).

## 9. Что осталось (S2b)

1. Время 12 МП ×4 / ×2 / быстрый 2× и 1 МП ×4 на устройствах T0/T1/T2 (Android ncnn CPU/Vulkan, iOS Core ML — после S4).
2. Тепловое замедление на 2–5-минутной нагрузке и NFR-BAT-001.
3. HEIC: лимиты размера и пиковая память HeifWriter и CGImageDestination с BandStore-провайдером.
4. Запись/чтение BandStore на eMMC (T0) и UFS; поведение при нехватке места.
5. Конвейер prep/infer/post с очередями для T2 (на быстром GPU 11% времени — CPU-накладные).
6. Причина ошибок ncnn Vulkan на больших формах (544², 1.2 МП целиком) — вместе с S3.
