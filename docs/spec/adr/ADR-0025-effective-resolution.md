# ADR-0025: Эффективное разрешение, резкость и встроенный денойз 0

- **Статус:** Accepted
- **Дата:** 2026-10-20

## Контекст

Жалоба: фото со старых «мыльниц» и смазанные снимки после обработки остаются нечёткими, их
лишь слегка сглаживает; лучше становятся только мелкие надписи. Целевой телефон (Helio G99)
относится к T1/T0, тяжёлые паки (`sr.x4plus`, `jpeg.fbcnn`, `face.codeformer`) ему не
предлагаются.

Исследование (фаза 1, 4 реальных фото и синтетика на Kodak) показало:

- SR-модель `realesr-general-x4v3` обучена на размытии ~1–2 px во входном масштабе. На снимке,
  размытом на 5–15 px, она принимает размытие за содержимое, а работает почти на пиксельном
  разрешении фото (ADR-0014).
- Если уменьшить вход до **эффективного** разрешения, сделать x4 и ресемплировать к прежнему
  размеру выхода, результат получается и чётче, и дешевле. На синтетике (8 Kodak, ↓2,
  10 видов размытия, шум σ 3, JPEG 70) LPIPS падает 0.408 → 0.343 (−16 %) при PSNR
  25.22 → 25.17. При f = 0.54 стоимость модели составляет 0.29× от прохода на полном входе
  (на хосте при 2 потоках 0.46× из-за паддинга тайлов).
- Уровень денойза 0 при σ < 2 Auto уже выбирал, но только когда установлен пак; при свежей
  установке работал уровень 0.5.
- Нерезкое маскирование по яркости после SR, с маской краёв и ограничением ореолов, даёт
  ещё −0.013 LPIPS при −0.2 дБ PSNR.

## Решение

1. **Оценка (`estimate_eff_scale`, `policy/analyze.cpp`; поле `eff_scale` в JSON анализа,
   схема 1, поле необязательное).** Считается на полном разрешении, по 16 тайлам 256 px с
   наибольшим контрастом.
   - Для f ∈ {1, 0.7, 0.5, 0.35, 0.25}: area-downscale тайла, затем на пикселях с локальным
     размахом 5×5 > 0.06 считается крутизна |Sobel|/8 / размах. Берётся медиана по верхним
     2 % краёв по градиенту, изотропно и отдельно по 4 ориентациям градиента (минимум по
     ориентациям ловит смаз движения).
   - Для каждой меры берётся наибольшее f, при котором крутизна ≥ τ (интерполяция по log f;
     τ_iso = 0.30, τ_dir = 0.32). Итог — среднее геометрическое двух f; без краёв — 1.
   - τ подобраны по оракулу: на 16 Kodak (не входящих в оценку) × 10 размытий для каждого
     случая находился f с лучшим LPIPS после SR. Оценка следует за силой размытия (медианы
     для gauss σ 1.5/3/5 — 0.90/0.53/0.33 при оракуле 0.70/0.50/0.30; disk r 6/10 —
     0.47/0.30 при 0.42/0.30). На этих данных LPIPS при f по оценке — 0.451, при f по
     оракулу — 0.438, при f = 1 — 0.515.
   - C++ совпадает с эталоном на numpy: медианы отличаются на ≤ 0.03, среднее |Δ| 0.017
     (`test_pipeline`: синтетическая сцена, коридор ±0.08). Время — 37 мс на 12 МП на хосте.
   - Скрипты: эталон оценки — `tools/ml/effscale.py` (`--test-scene` печатает эталоны
     `test_eff_scale`); τ пересчитываются `tools/ml/effscale_calibrate.py --cli … --models … WORK`
     (Kodak, оракул через refocal-cli, LPIPS).
2. **Политика (AutoPolicy).** При eff < 0.9 рецепт получает `preDown = max(0.4, eff)` (два
   знака) и причину `blurryPhoto`. Порог консервативный: принудительное f = 0.5 на резком
   фоне снимка со смазанным ребёнком превращает надпись на коробке в кашу, поэтому ошибка в
   сторону «размыто» опаснее. Каждый рецепт Auto получает `sharpen = 1`. Ручной режим
   редактора своих элементов управления для этого не получает.
3. **Рецепт и ядро.** `pre_down` ∈ (0, 1] и `sharpen` ∈ 0..1.5 в запросе джоба. Рецепт
   переходит на схему 7 и пишет её только при включённых полях, поэтому старые рецепты
   остаются читаемыми. `fast2` остаётся. Коэффициент для SR — min(fast2 ? 0.5 : 1, pre_down);
   с 8× `pre_down` не сочетается. Оба поля входят в `recipe_hash`, но только во включённом
   состоянии, так что полосы старых джобов при resume совпадают.
4. **Пайплайн (`job.cpp`).** Лица по-прежнему восстанавливаются с входа полного разрешения.
   Затем вход уменьшается (`resize_area`, точное усреднение по площади), SR делает x4 с
   наибольшим area /down, при котором выход ещё не меньше целевого. Если включён `pre_down`
   или `sharpen`, SR пишет полосы в отдельный BandStore `pre/` с собственным checkpoint, а
   **финальный проход** делает результат полосами по 256 строк:
   - Lanczos-3 из `pre/` (`LanczosResampler` с источником строк: читается по полосе, вперёд,
     в памяти не больше трёх полос SR);
   - USM (`unsharp_luma`) на окне ±6 строк вокруг полосы — без швов, детерминированно;
   - вставка лиц, превью, коммит.
   Размер результата — ровно тот, что был бы без `pre_down`. `pre/` удаляется по окончании.
   В `result.json` поле `pre_down` такое же, как в запросе (рецепт, как `scale` и `fast2`), а
   `sr_pre_down` — коэффициент, на котором фактически работал SR.
   Resume продолжает SR-проход, а потом финальный проход со своей полосы. Ветка «только лица»
   (Lanczos-фон) оба поля не применяет.
5. **USM** живёт в SR-стадии, а не в экспорте:
   - только так маска ложится на фон до вставки лиц и не пересушивает восстановленные лица;
   - смешение по силе при экспорте и превью редактора остаются как есть (ADR-0012), то есть
     сила смешивает уже резкий результат с Lanczos входа;
   - цена: изменить `sharpen` можно только повторной обработкой.

   Параметры: σ 1.5, маска clamp((|Sobel(G₁·y)|/8 − 0.01)/0.03, 0, 1), y' в пределах
   min/max 3×3 ± 0.02.
6. **Денойз 0 встроен в APK** (`models.lock`, `assets/models/sr.general-x4v3-dn0/`, BSD-3,
   +2.4 МБ). Id и файлы те же, что у пака: установленные копии продолжают работать. Пак
   остаётся в манифесте для старых версий, но список моделей его больше не предлагает.

## Последствия

- (+) Размытые фото обрабатываются чётче и дешевле, встроенными permissive-моделями, на всех
  тирах.
- (+) Auto берёт денойз 0 при σ < 2 без загрузки.
- (−) Оценка глобальная: при локальном смазе (резкий фон, смазанный объект) она даёт 1, и
  объект остаётся смазанным.
- (−) Уменьшение не восстанавливает того, чего на снимке нет. Лица в несколько десятков
  пикселей остаются «живописными»; заметно меняет их только восстановление лиц (NC-пак).
- (−) Джоб с `pre_down`/`sharpen` временно занимает на диске ещё один SR-выход (`pre/`); при
  `sharpen` без `pre_down` он равен размеру результата.
- (−) Длинный смаз движения насыщается на 0.5 (изотропная мера видит края вдоль движения).

## Отложено (фаза 1, с цифрами)

- **NAFNet-GoPro-w32 перед SR при eff < 0.8** (MIT, 34 МБ fp16). На синтетике LPIPS
  0.343 → 0.316 (смаз движения 0.397 → 0.338), с USM — 0.303. На реальных фото эффект
  слабый. Нужна подпись нового пака (ключ манифеста), лицензии GoPro/SIDD не проверены.
- **`sr.x4plus` при f ≤ 0.36 на T2:** LPIPS 0.290, но в 11–24 раза дороже x4v3 при том же
  входе и дорисовывает буквы («HUGS» → «HUGA»).
- **Автопредложение 2× вместо 4× при eff < 0.6:** меняет UX.
- **Оценка резкости по областям** (объект против фона).

## Отклонённые альтернативы

- 4xLSDIRCompact R3/C3/CR3/v2, 2xNomosUni-compact-otf, 4xNomosWebPhoto-RealPLKSR (CC-BY-4.0):
  не MIT/BSD/Apache (ML-REG-003); на реальных фото рисуют «маски» на лицах; RealPLKSR ещё и
  в 11–14 раз дороже, а GroupNorm делает результат зависимым от тайла.
- Restormer (defocus, MIT): 26 млн параметров, PSNR −2 дБ на синтетике.
- USM в экспорте: лица были бы пересушены, а превью пришлось бы считать ещё раз.
