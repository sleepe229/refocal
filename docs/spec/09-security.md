# 09. Безопасность

## 1. Активы

| Актив | Почему важен |
|---|---|
| Фото пользователя | Приватные данные; утечка недопустима |
| Целостность моделей | Подменённая модель → вредоносный/оскорбительный результат или эксплойт рантайма |
| Ключи подписи (манифест, релизы) | Компрометация → распространение вредоносных паков/сборок |
| Репутация проекта | Доверие к «приватному» приложению |

## 3. Требования

### 3.1 Цепочка поставки моделей (SUP)

| ID | Требование | Приоритет | Релиз | Проверка |
|---|---|---|---|---|
| SEC-SUP-001 | Каждый файл пака проверяется по SHA-256 из манифеста **до** загрузки в рантайм и при каждом старте (быстрая проверка размера + mtime; полная — после обновления приложения) | Must | R0.2 | TEST-SEC-003 |
| SEC-SUP-002 | Манифест подписан minisign (Ed25519); в приложение вшиты 2 публичных ключа (текущий + резервный); подпись проверяется до парсинга JSON | Must | R0.2 | TEST-SEC-003 |
| SEC-SUP-003 | `serial` манифеста монотонен; манифест с меньшим `serial` отклоняется | Must | R0.2 | TEST-SEC-004 |
| SEC-SUP-004 | Модели загружаются в рантайм только из зарегистрированных проверенных паков | Must | R0.2 | ревью |
| SEC-SUP-005 | Приватный ключ подписи манифеста хранится офлайн (аппаратный ключ / зашифрованный носитель), у хранителя (сейчас — мейнтейнер) с зашифрованной офлайн-копией, второй хранитель — до 1.0 (Q-05); процедура подписи и ротации описана в `docs/ops/signing.md` | Must | R0.2 | Q-05 |
| SEC-SUP-006 | Ротация ключа: новый манифест подписывается старым и новым ключом в переходный период; приложение с новым ключом выходит до отзыва старого | Should | R1.0 | — |

### 3.2 Входные данные (INP)

| ID | Требование | Приоритет | Релиз | Проверка |
|---|---|---|---|---|
| SEC-INP-001 | Декодеры (libjpeg-turbo, libpng, libwebp) и `metaio` фаззятся libFuzzer в CI (каждый PR — 5 мин, nightly — 1 ч, перед 1.0 — 24 ч без падений) | Must | R0.3 | TEST-SEC-001/002 |
| SEC-INP-002 | Лимиты до декодирования: ширина/высота ≤ 30000, пиксели ≤ 200 МП, размер файла ≤ 200 МБ, размер EXIF/XMP ≤ 1 МБ | Must | R0.1 | TEST-SEC-001 |
| SEC-INP-003 | Native-код собран с `-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2`, PIE, RELRO/now; CFI где поддерживается | Must | R0.1 | CI-проверка флагов |
| SEC-INP-004 | Сборки ASan/UBSan core-тестов и фаззеров в CI | Must | R0.1 | TEST-SEC-006 |
| SEC-INP-005 | `.rfpack`: подпись проверяется до распаковки; пути нормализуются, запрещены `..`, абсолютные пути, симлинки; лимит распакованного размера 2 ГБ и коэффициент сжатия ≤ 100 | Must | R0.3 | TEST-SEC-005 |
| SEC-INP-006 | Third-party библиотеки обновляются при CVE в течение 14 дней (critical — 72 ч) | Must | R0.5 | Dependabot/OSV-scanner |

### 3.3 Сеть (NET)

| ID | Требование | Приоритет | Релиз |
|---|---|---|---|
| SEC-NET-001 | Только HTTPS (TLS 1.2+), системные хранилища сертификатов; без отключения проверки | Must | R0.2 |
| SEC-NET-002 | Certificate pinning не применяется (целостность гарантирует подпись манифеста; pinning ломает зеркала) | — | — |
| SEC-NET-003 | Таймауты и лимит размера ответа манифеста (≤ 1 МБ) | Must | R0.2 |

### 3.4 CI и релизы (CI)

| ID | Требование | Приоритет | Релиз |
|---|---|---|---|
| SEC-CI-001 | GitHub Actions закреплены по commit SHA; `permissions:` минимальны по умолчанию (`contents: read`) | Must | R0.1 |
| SEC-CI-002 | Workflow для PR из форков не имеют доступа к секретам; `pull_request_target` не используется с checkout кода PR | Must | R0.1 |
| SEC-CI-003 | Секреты подписи — в GitHub Environments `release` с обязательным ревьюером; Play App Signing; App Store Connect API key с ролью App Manager | Must | R0.3 |
| SEC-CI-004 | SBOM (CycloneDX) и build provenance attestations (`actions/attest-build-provenance`) для каждого релиза | Must | R0.5 |
| SEC-CI-005 | Защита ветки `main`: обязательные проверки, ревью ≥ 1 мейнтейнера, подписанные коммиты для мейнтейнеров (рекомендуется) | Must | R0.1 |
| SEC-CI-006 | Сканирование секретов (GitHub secret scanning + push protection) | Must | R0.1 |

## 4. Политика раскрытия уязвимостей

`SECURITY.md`:

- канал — GitHub Private Vulnerability Reporting;
- подтверждение получения — 72 ч; оценка — 7 дней; исправление critical/high — 30 дней; публичное раскрытие — 90 дней или после исправления;
- поддерживаемые версии: последний минорный релиз;
- благодарности в CHANGELOG (по желанию исследователя).
